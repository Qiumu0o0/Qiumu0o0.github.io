## 大意

这篇文章是 Danzinger 和 Musliu 在 CP 2026 发表的研究，核心是：

**利用 LLM 生成 MiniZinc 冗余约束，再通过 Lean 4 形式化证明其正确性，从而自动优化约束模型。**

这里有几个问题值得关注：

- 什么是冗余约束？
- 形式化证明正确性-> 这里被证明的是什么东西？
- 优化约束模型-> 这里的优化指的是什么？

As for the optimization, 在保持模型解集不变的前提下，改善求解器的运行表现:

- Solving time;
- whether can find a soluable solution;
- whether can prove that the found solution is optimal;
- the value of the objective function;

---

**Redundant Constraints** are the constraints that can be infered from the existing constraints, i.e. after adding the redundant constraints, the solution set of the model invariant. 

M = C_1 /\ ... /\C_n

If the new constraint C_n+1 can be inferred from the model:

M |= C_n+1

then C_n+1 is a redundant constraint.(try to prove that Sol(M) = Sol(M /\ C_n+1))

**So why we want this kind of constraints?** 但可能增强求解器的传播能力，从而提高求解效率。So how to improve the efficiency?

因为约束求解器并不是简单地枚举所有可能解，而是通过约束传播（Constraint Propagation）不断缩小变量的取值范围。**新增约束可能提供额外的信息，使求解器更早排除不可能的搜索分支，从而提高效率。**

For example, the solver should try x = 1 and x = 0 to make sure wether this two cases can fit the requirements, so there are two branches needed to be searched. But if we add a new constraint x != 0, then only one branch need to be searched.

Given a model, LLM can generate some constraints, but cannot make sure that they are **really redundant**. So how to make sure that the constraints generated by LLM are really redundant?

## Core methods

- 生成：LLM 根据原始 MiniZinc 模型提出新约束。
- 评估：在训练实例上测试性能，筛选有效约束。
- 翻译：将 MiniZinc 模型和新约束转换为 Lean 4 定理。
- 证明：利用 LLM 生成 Lean 证明，由 Lean 内核检查。

这里的评估步骤是什么意思？即这里的训练实例是什么？怎么测试？什么是有效约束？以及，翻译步骤得到的定理具体是什么？

大意中的第二个问题，What is proved? 即这里被翻译出的 Lean4 定理：

Forall I, forall x, M(I,x) => C_new(I,x)

where I is an instance(a set of value of parameters), x is the value of decision variables, M are the constraints and C_new is the new constraint.

---

每个问题的实例被划分为 Training set and Test set. 训练实例用于筛选新约束，测试实例用于评估最终模型的表现。

instance 通常在minizinc 中由data, 即 .dzn 文件的形式表示。

> 训练实例和测试示例有什么区别？
> 训练实例如何筛选新约束？测试实例又是如何评估模型表现？

**评估**：作者将新增约束后的模型与原模型进行比较。

具体来说：
1. 使用 Chuffed 求解器运行原模型。
2. 使用相同求解器运行添加新约束的模型。
3. **比较**两者在**训练实例**上的求解结果。
4. 根据**统计检验**判断性能是否改善

这里是如何进行比较的？也就是说两个求解结果的好坏怎么比较？什么是统计检验？

这里的**有效约束**指的是：在实验中能够带来足够明显的**求解性能改善**的候选约束。注意，实验表现好并不意味着约束一定正确，所以还需要后面的形式化验证。

论文中采用了一个基于 MiniZinc Challenge 的评分机制：

- status
- objective value
- runtime

最优或者证明无解 > 可行 > 超时（规定时间内无解），即 closed, feasible and failed.

对于都有解的情况，目标函数更优的为佳；对于均为最优解的情况，求解时间短的为佳；对于每个求解，作者提出了一套评分机制，每个求解都会获得一个分数。对所有实例上的得分差异进行统计检验。如果通过检验，就认为候选约束在实验性能上有效。注意：此时还没有证明它是冗余约束。

> 这套评分机制为什么合理？

也就是说，训练集是用来筛选有效约束的。而测试集不参与约束的筛选，是用来比较最终得到的新的增强模型和原模型相比的提升的。

## 结果

作者测试了三个经典组合优化问题：

- Oven Scheduling; 求解时间下降 12.5%，目标值改善2.2%；

其余两个例子暂略。这里有几个问题值得关注：

- 什么让求解时间下降了？目标值改善是指什么？

对于最优化问题，目标值改善即找到一个让目标函数更小的解。当然，增添 redundant constraint 没有改变解集，但是却改善了求解速度。事实上，我们的程序求解的是有限时间内可求解的最优解，所以改善求解速度之后，是有可能找到更优解的。

## 主要贡献

- 建立Minizinc to lean 的翻译机制；
- 实现了对redundant 约束的机器检查证明；
- 结合 LLM 的创造力和形式化验证；

## 局限

目前只支持 minizinc 的一个子集；
需要假设原来的模型是安全的，没有完整验证翻译器的语义正确性；

**这篇文章探索的是如何让 LLM 不仅能提出优化方案，还能用形式化方法证明优化不会破坏模型正确性。**
